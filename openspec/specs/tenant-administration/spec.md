# tenant-administration Specification

## Purpose

Defines what a Giano platform admin can do to tenants at runtime through `/v1/platform/tenants`: create, read, update, issue and revoke admin keys, adopt seeded tenants, and read history. Every write keeps the invariant tenant ≡ wallet origin ≡ RP ID exactly as the boot seed does.

## Requirements

### Requirement: Every tenant write passes one validator
The seed, create and update paths SHALL apply the same field rules and the same single-tenant invariants. The invariants are:
- `rpId` equals the `walletOrigin` host;
- every `expectedOrigins` host equals `rpId` or is a subdomain of it;
- every origin field is a bare origin;
- a tenant with `openRegistration: false` has at least one admin key.

Unknown fields SHALL be rejected on every path. Update SHALL validate the merged result of the stored tenant and the patch, with the admin-key count taken from storage. A validation failure SHALL return `400` with one issue per violation, each carrying a field path and a message, and nothing SHALL be written.

#### Scenario: RP ID differs from the wallet host
- **WHEN** a platform admin creates a tenant whose `rpId` is not the host of its `walletOrigin`
- **THEN** the response is 400 with an issue at `rpId`, and no tenant is created

#### Scenario: Expected origin outside the RP ID
- **WHEN** a create or patch lists an `expectedOrigins` entry whose host is neither the `rpId` nor a subdomain of it
- **THEN** the response is 400 with an issue at `expectedOrigins`

#### Scenario: Patch would leave a closed tenant without keys
- **WHEN** a patch sets `openRegistration: false` on a tenant that has no admin keys
- **THEN** the response is 400 with an issue at `adminKeys`, and the tenant is unchanged

#### Scenario: Unknown field
- **WHEN** a create body, a patch body or a seed entry carries a field the schema does not define
- **THEN** the write is refused with an issue naming the field. For the seed, `wallet-api` refuses to start.

### Requirement: No origin is claimed by two tenants
A tenant's origin claims SHALL be its `walletOrigin` together with its `expectedOrigins`. No origin SHALL be claimed by more than one tenant, counting tenants in every lifecycle state, deleted ones included. Concurrent writes SHALL be serialised so that the check cannot be raced. `corsOrigins` and `allowedDappOrigins` SHALL NOT count as claims.

A violating create or update SHALL return `409 origin-claimed`, naming the origin and the other tenant's slug. A violating seed SHALL refuse boot with an error that names the origin, the other tenant's slug, and that tenant's management and lifecycle state.

#### Scenario: Concurrent creates claiming one origin
- **WHEN** two platform admins create different tenants claiming the same origin at the same moment
- **THEN** exactly one receives 201 and the other receives 409 `origin-claimed`

#### Scenario: Seed overlapping another seed
- **WHEN** a seed entry's `expectedOrigins` contains another seed entry's `walletOrigin`
- **THEN** `wallet-api` refuses to start and names both tenants

#### Scenario: Deleted tenant's origin stays claimed
- **WHEN** a platform admin creates a tenant claiming an origin that a deleted tenant claimed
- **THEN** the response is 409 `origin-claimed`

#### Scenario: Shared CORS origin
- **WHEN** two tenants list the same `corsOrigins` entry
- **THEN** both writes succeed

### Requirement: Identity fields are immutable
`slug`, `id`, `walletOrigin` and `rpId` SHALL NOT be changeable through the API. A patch naming any of them SHALL return `422 immutable-field` and change nothing. Database uniqueness violations on `slug`, `id`, `walletOrigin` or `rpId` SHALL return `409 conflict`, naming the field, and never `500`.

#### Scenario: Patch names the wallet origin
- **WHEN** a patch body contains `walletOrigin`
- **THEN** the response is 422 `immutable-field`

#### Scenario: Duplicate slug
- **WHEN** a platform admin creates a tenant with a slug that already exists, in any state
- **THEN** the response is 409 `conflict` naming `slug`

### Requirement: Platform admins can create a tenant
`POST /v1/platform/tenants` SHALL create an active, platform-admin-managed tenant from:
- the tenant fields;
- an optional fixed `id`, for a tenant already registered on-chain;
- `adminKeys` given as a list of `{ label }`.

The response SHALL be `201 { tenant, adminKeys: [{ id, label, key }] }`.
- Each key is generated by the server: 32 random bytes, base64url, prefixed `gak_`.
- The plaintext appears only in this response; only its hash is stored.
- The API SHALL never accept a caller-chosen admin key.

The new tenant SHALL be resolvable on the next request, on every replica, with no restart.

#### Scenario: Create and resolve without restart
- **WHEN** a platform admin creates tenant `runtime` with `walletOrigin` `http://wallet-runtime.localhost`, then a client requests `/.well-known/webauthn` with that Host and `POST /v1/webauthn/options` with that Origin
- **THEN** the create returns 201 with one plaintext `gak_` key per requested label, and both later requests resolve to `runtime` without any process restarting

#### Scenario: Keys are shown once
- **WHEN** the platform admin reads the tenant after creating it
- **THEN** the admin keys are listed by id, label, hash prefix, creator and creation time, never as plaintext

### Requirement: Platform admins can read tenants
`GET /v1/platform/tenants` SHALL list tenants newest first. By default it SHALL exclude deleted tenants, and `?status=` SHALL filter by state.

`GET /v1/platform/tenants/:slug` SHALL return:
- every tenant field, plus `managedBy`, `status` and `version`;
- the admin keys, without key material;
- user and credential counts;
- the time of the tenant's last user operation;
- the ledger position on each chain.

An unknown slug SHALL return 404.

#### Scenario: Deleted tenants hidden by default
- **WHEN** a platform admin lists tenants without a status filter and one tenant is deleted
- **THEN** the deleted tenant is absent, and it appears with `?status=deleted`

### Requirement: Updates are optimistic and versioned
`PATCH /v1/platform/tenants/:slug` SHALL accept only these fields: `rpName`, `expectedOrigins`, `allowedDappOrigins`, `corsOrigins`, `openRegistration`, `policy` and `branding`. It SHALL require `If-Match: "<version>"`. Every tenant write SHALL increment `version`, seed writes included. The response codes are:
- no `If-Match`: `428 precondition-required`;
- a stale version: `412 version-mismatch`, with the current version in the body;
- success: `200` with the updated tenant.

#### Scenario: Concurrent edits
- **WHEN** two platform admins patch the same tenant with the same `If-Match` version
- **THEN** one receives 200, and the other receives 412 with the new version

#### Scenario: Missing precondition
- **WHEN** a patch arrives without `If-Match`
- **THEN** the response is 428

### Requirement: Platform admins manage admin keys of platform-admin-managed tenants
For an active, platform-admin-managed tenant:
- `POST /v1/platform/tenants/:slug/admin-keys` with `{ label }` SHALL issue a generated key, returned once as `201 { id, label, key }`.
- `DELETE /v1/platform/tenants/:slug/admin-keys/:keyId` SHALL revoke it with `204`.
- Revoking the last key of a tenant with `openRegistration: false` SHALL return `409 last-admin-key`.

A revoked key SHALL stop authorising `/v1/admin/*` on the next request.

#### Scenario: Issue then use
- **WHEN** a platform admin issues a key and a client calls `/v1/admin/sponsorship` with it
- **THEN** the call is authorised for that tenant

#### Scenario: Revoke the last key of a closed tenant
- **WHEN** a platform admin revokes the only admin key of a tenant with `openRegistration: false`
- **THEN** the response is 409 `last-admin-key`, and the key still works

### Requirement: Every tenant write is recorded and attributed
Every tenant write SHALL append a history entry in the same transaction as the write. That covers create, update, suspend, resume, delete, admin-key issue and revoke, seed apply, seed takeover and adopt. Each entry records:
- the action;
- the actor: `seed`, or `platform-admin:<id>:<address>`;
- the platform admin session, for platform admin writes;
- the tenant before and after the write;
- for key actions, the key id, label and hash prefix.

Entries SHALL never contain key material. A boot that changes nothing SHALL write no entry. `GET /v1/platform/tenants/:slug/history?before=` SHALL return entries newest first, 50 per page, with a cursor for the next page.

#### Scenario: Attribution
- **WHEN** platform admin `ops-a` suspends a tenant
- **THEN** the newest history entry has action `suspend`, actor `platform admin:ops-a:<address>` and that platform admin's session

#### Scenario: Idle restart
- **WHEN** `wallet-api` restarts with an unchanged `TENANTS_SEED`
- **THEN** no history entry is written
