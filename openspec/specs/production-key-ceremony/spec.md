# production-key-ceremony Specification

## Purpose

Every private key that can move mainnet value or hold a privileged role in a live Giano deployment comes from the
ABIP-8 Key Generation Ceremony and is never seen by the development team or a client. The repository's tooling and
documentation do not push anyone toward handling such a key by hand. This is the repository's implementation of
ABIP-8.

## Requirements

### Requirement: Live-service keys are inventoried
The repository SHALL keep an inventory of every key that a live Giano deployment uses, in `docs/key-ceremony.md`. For
each key it SHALL give:
- its name;
- what it signs, or which role it holds;
- whether it is in ABIP-8 scope;
- the secret store that holds it in each environment class;
- which service consumes it.

The inventory SHALL include at least:
- the canonical deployer;
- the sponsorship signer;
- the bundler executor;
- the paymaster `ROLE_ADMIN`, and the proposer and executor keys of the TimelockController that holds it in
  production.

Platform-admin API keys are bearer tokens, not private keys. They SHALL be listed as out of scope, with that reason.

#### Scenario: Unknown key found
- **WHEN** a service or tool reads a private key from an environment variable or secret that the inventory does not
  list
- **THEN** the key is treated as in ABIP-8 scope until it is classified, and the inventory is updated in the PR that
  introduces it

#### Scenario: Dev keys classified
- **WHEN** the inventory lists the anvil dev keys of `docs/E2E-DEV-KEYS.md` and the `dev` environment's Base Sepolia
  and Ethereum Sepolia keys
- **THEN** each is marked out of scope as a local or testnet-only key that can never hold real value

### Requirement: In-scope keys come only from the ceremony
Every in-scope key SHALL be generated by the DevOps team in an ABIP-8 ceremony, using `multichain-keygen` with
`--rng openssl`, on a dedicated clean VM. The key SHALL be an independent random key, not HD-derived or
mnemonic-derived, unless an exception has been approved and recorded. The key SHALL be piped directly into the
environment's secret store, either the 1Password vault that `infra/iac` mirrors into AWS Secrets Manager or a KMS/HSM
key. Each ceremony SHALL be recorded on a Notion page that uses the ABIP-8 template. That page SHALL hold the public
address and SHALL NOT hold the private key.

`docs/key-ceremony.md` SHALL hold the Giano-specific runbook:
- which keys to generate;
- which vault item and field each key goes into;
- how its address is published to the service owner;
- for the canonical deployer, how the address replaces the placeholder in `deploy/config.ts` (the README's switch
  procedure).

The runbook SHALL link ABIP-8 rather than restate it.

#### Scenario: Real canonical deployer adopted
- **WHEN** the placeholder `CANONICAL_DEPLOYER` (`0x…dEaD`) is replaced in `deploy/config.ts`
- **THEN** the PR links the ceremony record whose public address equals the new value

### Requirement: The development team and clients never hold production keys
No repository tool, script, compose file, Helm chart or document SHALL require or instruct a developer or a client
operator to hold an in-scope private key. The development team SHALL NOT have read access to the prd secret vault. The
documented deployment paths SHALL NOT put the canonical deployer key in a client's Kubernetes secret or `.env` file.
These are the Helm `deployer` job, `deploy/docker-compose.*.yml` and the `deploy/contracts` workflows.

#### Scenario: Helm install against an adopted chain
- **WHEN** a client installs the Helm chart with `deployer.enabled=true` against a chain where every canonical contract
  is already deployed
- **THEN** the deployer job verifies the addresses and code, writes the registry entry and succeeds without any
  `DEPLOYER_PRIVATE_KEY` in the secret

#### Scenario: Helm install against an unadopted chain
- **WHEN** the same install targets a chain where a canonical contract is missing
- **THEN** the job fails, explaining that adopting a chain needs the canonical deployer, which is operated by Applied
  Blockchain DevOps, and it does not ask for the key

### Requirement: Production-class signing never uses an in-process key
In a `production` deployment class, wallet-api SHALL continue to refuse `SPONSORSHIP_SIGNER_KIND=local`. The ABIP-8
runbook SHALL state that the production sponsorship signer is created inside the HSM or KMS, or imported there by
DevOps from a ceremony, and is never exported.

#### Scenario: Local signer refused in production
- **WHEN** wallet-api boots with `GIANO_DEPLOYMENT_CLASS=production` and `SPONSORSHIP_SIGNER_KIND=local`
- **THEN** it refuses to start

### Requirement: Key-handling instructions point to the ceremony
Every document that tells a reader to set an in-scope key on a command line, in an env file or in a shell SHALL be
rewritten. It SHALL either name the ceremony and the secret store as the only source of the key, or limit itself to
local and testnet use. Because one canonical deployer key owns the salts on every chain, it is in scope on testnets
too. The documents are:
- `specs/INFRASTRUCTURE.md` (§13.1 and the runbook);
- `specs/INTEGRATION.md`;
- `specs/DEVELOPER-GUIDE.md`;
- `specs/CHAIN-ADOPTION.md`;
- `packages/contracts/README.md`;
- the Helm `values.yaml`;
- the deploy CLI's usage text;
- `deploy/contracts/README.md`, once #160 adds it.

`deploy/sepolia/`, which keeps `CANONICAL_DEPLOYER_PRIVATE_KEY` in a developer's `deploy/.env`, is removed by #160.
Until then, `docs/key-ceremony.md` flags it as superseded, and DevOps must run it.

#### Scenario: README instruction
- **WHEN** a reader follows the contracts README's deploy section for a mainnet chain
- **THEN** it sends them to `docs/key-ceremony.md` and DevOps, and gives no `DEPLOYER_PRIVATE_KEY=…` command for mainnet
