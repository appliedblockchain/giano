## Why

Tenants are provisioned only by `TENANTS_SEED`, applied at boot, so adding, changing or switching off a tenant means editing the environment and redeploying `wallet-api`. H5 R1 asks that Giano's own operators can create, read, update and delete tenants at runtime, without a redeploy, while keeping the invariant tenant ≡ wallet origin ≡ RP ID that the seed path protects today. The `/v1/admin/*` routes cannot do this: each is scoped to the single tenant whose admin key authorised it, and no operator tier sees across tenants.

This change is PR 1 of H5 as planned in `specs/OPERATOR-ADMIN-SPECS.md` §1.1. It covers deliverables D2 → D3 → D1 → D4, which satisfy R1 through the API. The console (D6) is PR 2. Blockchain status (D5) is a separate card (H-k).

## What Changes

- **Operator sign-in.** Operators sign in with an Ethereum wallet (EIP-4361) and get a 30-minute session. `OPERATOR_ADDRESSES` lists the operator EOAs. `POST /v1/operator/auth/{challenge,verify,logout}` issue the message, verify it, and end the session. Verify accepts only the exact text the server issued. A new `requireOperator` guard runs alongside `requireAdmin`, and the two never share a lookup. Every `/v1/operator/*` route refuses any request carrying `Origin`. When `OPERATOR_ADDRESSES` is empty, none of these routes is registered.
- **Tenant lifecycle.** Tenants have three states: `active`, `suspended`, `deleted`. Delete leaves a tombstone, so a deleted slug, id, wallet origin and RP ID are never reusable. A tenant must be suspended before it is deleted, and delete refuses in these cases:
  - the tenant has a ledger balance or deficit on any chain;
  - it has an unexpired reservation;
  - the ledger is stale.
- **Lifecycle-aware resolution.** Every tenant resolver (Origin, Host, admin key, session, CORS) returns active tenants only. A suspended tenant behaves as an unknown one. **BREAKING (internal):** `requireSession` refuses a session whose tenant is not active, including on requests that carry no Origin, which today fall through unchecked.
- **One validator for every write.** `tenantSeedSchema` splits into a field schema and an invariant check, shared by the seed, create and update paths.
  - The validator gains a cross-tenant check, under an advisory lock: no origin may be claimed by two tenants, deleted ones included.
  - **BREAKING (deploy):** a seed that overlaps another tenant's origin claims now refuses to boot.
  - **BREAKING (deploy):** so does a seed entry with keys outside the field schema, which today are silently dropped.
- **Operator tenant routes.** The new routes live under `/v1/operator/tenants`:
  - list, detail, create, `PATCH` with `If-Match`;
  - suspend, resume, delete;
  - admin-key issue and revoke, with keys generated by the server and shown once;
  - adopt from the seed;
  - paginated history.
- **Seed and runtime ownership.** Each tenant is managed by the seed or by operators. Through the API, a seed-managed tenant can only be suspended and resumed. A seed entry takes over an operator-managed tenant with the same slug at boot, and a seed entry for a deleted slug refuses boot.
- **History.** An append-only `tenant_history` records every write, seed writes included, with the operator's id, address and session.
- **Migration `0007_tenant_lifecycle.sql`.** Tenants gain `status`, `managed_by`, `version` and `status_changed_at`. Admin keys gain `created_by`. Three tables are new: `operator_challenges`, `operator_sessions`, `tenant_history`.
- **Challenge cleanup.** A periodic job deletes long-expired tenant and operator challenges. Today `challenges.prune()` exists and nothing calls it.
- **Login script.** `scripts/operator-login.ts` (`operator:login`) signs in from a private key, for acceptance on dev.

## Capabilities

### New Capabilities
- `operator-authentication`: who an operator is and how they prove it. Covers the configured operator addresses, the EIP-4361 challenge and verify, session issue, expiry and revocation, the `requireOperator` guard, the Origin refusal, and how failures look.
- `tenant-administration`: what an operator can do to tenants through `/v1/operator/tenants`. Covers create, read, update with optimistic concurrency, admin-key issue and revoke, adopt, history, attribution, and the shared validation every write passes, including disjoint origin claims and immutable fields.
- `tenant-lifecycle`: the states a tenant moves through and what each state means everywhere else. Covers resolution of active tenants only, suspension and resume, tombstone delete and its preconditions, and coexistence with `TENANTS_SEED` at boot.

### Modified Capabilities
None. `openspec/specs/` holds only the demo capabilities. Tenancy is documented in prose under `specs/*.md`, and those documents are updated in the tasks, not as OpenSpec deltas.

## Impact

- **Code (`services/wallet-api`)**:
  - `migrations/0007_tenant_lifecycle.sql` and `src/db/schema.ts`
  - `src/config.ts`: the `OPERATOR_*` variables and `TENANT_DELETE_MAX_LEDGER_LAG_BLOCKS`
  - `src/services/tenants.ts`: the schema split, invariants, origin claims, ownership rules and lifecycle-aware resolvers
  - new `src/services/operator-sessions.ts`
  - `src/plugins/auth.ts`: `requireOperator`, and the `requireSession` change
  - new `src/routes/operator-auth.ts` and `src/routes/operator-tenants.ts`
  - `src/app.ts`: route registration and the `operatorSession` security scheme
  - `src/index.ts`: the cleanup job
  - new `scripts/operator-login.ts`
  - tests under `test/`
- **APIs**: 14 new routes under `/v1/operator`, and `openapi/openapi.json` regenerated. Existing routes keep their shapes. A suspended tenant's callers get the responses an unknown tenant gets today.
- **Database**: one migration. It adds columns to `tenants` and `tenant_admin_keys` with defaults that backfill existing rows as active and seed-managed, and it adds three new tables.
- **Dependencies**: none new. `viem/siwe` comes with viem 2.31.6, which is already a dependency.
- **E2E**: the two-tenant compose stack lists an anvil account in `OPERATOR_ADDRESSES`. `e2e/tests/operator.spec.ts` covers suspend and resume, and a runtime create with no restart.
- **Deploy**: devops sets `OPERATOR_ADDRESSES` and `OPERATOR_SIWE_DOMAIN` on `wallet-api` and restricts `/v1/operator/*` at the `api.*` listener (O-3). The AWS dev `tenants-seed` secret must be checked for overlapping origins and unknown keys before this deploys (O-8).
- **Docs**:
  - `specs/ARCHITECTURE.md`: an operator row in the *decided from* table
  - `specs/DEVELOPER-GUIDE.md` §1: tenants are no longer seed-only
  - `services/wallet-api/README.md`: the new environment variables
  - `specs/INFRASTRUCTURE.md`: R31 stays as is until PR 2
- **Out of scope**:
  - the console Operator area (D6, PR 2);
  - `/v1/operator/chains` (D5, its own card);
  - serving a runtime tenant's wallet origin (O-5);
  - sponsorship rules for runtime tenants, which the tenant writes with its own admin key;
  - on-chain registration, which stays a wallet-signed console action;
  - `infra/iac/`.
