## Why

Applied Blockchain has adopted six ABIPs (Applied Blockchain Improvement Proposals): ABIP-1, ABIP-2, ABIP-5, ABIP-6,
ABIP-7 and ABIP-8. ABIP-3 and ABIP-4 do not exist in the register. The source of truth is the Notion register at
https://app.notion.com/p/applied-blockchain/ABIPs-31ab61bd7d5280aca3a9dd968a77b062.

Only ABIP-2 (Docker Hardened Images, #123) has been applied to Giano. The other five are partly met or not met at all.
Giano is a self-custodial wallet whose server holds the sponsorship signer, the bundler executor key and, soon, the
permanent CREATE3 canonical deployer key. That puts it in the "financial transactions" tier the ABIPs single out.
Giano has no production environment yet: `infra/versions.json` has `stg` and `prd` empty, and `CANONICAL_DEPLOYER` is
still a placeholder. That makes now the cheapest time to apply all six, before a live deployment or a real key exists.

Audit of `main` @ 73059bf (2026-10-27):

|------|---------------------|-------------|-----|

| 2 Hardened images | DHI on every stage, digest pins, non-root, SBOM; exceptions documented and tracked | adopted (#123), with CI policy check, signing and SBOM | the exception tracking issue was never opened; `giano-contracts-deployer` (which receives the deployer key) is still on `node:22-slim` as root, using a shell entrypoint |

## What Changes

The six ABIPs become six PRs in one GitHub stack (`gh stack`). Each is independently reviewable, ordered so that
dependencies come first and anything blocked on DevOps sits at the top: **5 → 6 → 7 → 2 → 8 → 1**.

- **ABIP-5 (PR 1):** add the root `AGENTS.md` from the ABIP-5 template, covering the scope rule, team, GitHub, Notion,
  Slack (#giano-dev, read-only) and the pull-request lifecycle and naming. `CLAUDE.md` becomes `@AGENTS.md`, and its
  no-attribution rule moves into `AGENTS.md`. The values the repo can't supply are collected from the user at apply
  time.
- **ABIP-6 (PR 2):** raise `minimumReleaseAge` to **10080 (7 days)** in both pnpm workspaces. Drop the third-party
  blanket `minimumReleaseAgeExclude` entries. Only version-specific exclusions (`name@x.y.z`) are allowed for those,
  each with a reason and a removal date. A CI check enforces the floor and the exclusion format. Our own
  `@appliedblockchain/*` scope stays excluded in `services/custom-example`, as a recorded deviation from ABIP-6, so the
  example can install a Giano release as soon as it is published.
- **ABIP-7 (PR 3):** pin every `dependencies`, `devDependencies` and `optionalDependencies` entry to an exact version,
  in all 14 manifests. Pin `peerDependencies` exactly in private packages. Keep peer ranges only in the seven published
  `@appliedblockchain/*` libraries. Pin override values to exact versions. A new `scripts/check-pinned-versions.mjs`
  CI check fails on any range. The lockfile is regenerated in that PR, and nothing else changes in it.
- **ABIP-2 (PR 4):** close the ABIP-2 gaps.
  - Move `giano-contracts-deployer` onto DHI Node. Its blocker, `hardhat-foundry` shelling out, went away with the
    Foundry/CREATE3 move in #132.
  - Port its entrypoint from `sh` to `.mjs` and remove its whole-file exemption.
  - Open the tracking issue for the `giano-devnet` exception and link it from `docs/abip-compliance.md`.
- **ABIP-8 (PR 5):** add the key inventory and the ceremony runbook. Every live-service key is listed with its scope:
  canonical deployer, sponsorship signer, bundler executor, paymaster `ROLE_ADMIN` and its timelock proposers.
  Guardrails:
  - the deploy CLI and deployer image need no key for a verify-only run against an adopted chain;
  - the Helm deployer job's docs stop telling clients to put the canonical deployer key in their secret;
  - the docs that tell a person to export the key (`specs/INFRASTRUCTURE.md` §13.1, the contracts README) point to
    the ceremony instead.

  The ceremony itself, for the real `CANONICAL_DEPLOYER`, is a DevOps request rather than repository work.
- **ABIP-1 (PR 6):** create the `production` branch from `main` (`main` stays the default branch) and move only **prd**
  onto it:
  - `deploy.yml` deploys prd only on a push to `production`;
  - the prd OIDC role trusts `refs/heads/production` only;
  - dev and stg keep deploying from `main`.

  Also document the promotion flow (a PR `main` → `production`). Asking DevOps for the branch ruleset (PR required, one
  approval, no bypass) is a task, because only an admin can create it.
- `docs/abip-compliance.md` becomes the record for all six ABIPs. Each PR adds its own section and summary row.

## Capabilities

### New Capabilities
- `agent-guidance`: the repository's `AGENTS.md` / `CLAUDE.md` contract (ABIP-5): the required sections, the scope
  rule, permissions per external system, the pull-request conventions, and no secrets.
- `dependency-pinning`: exact versions in every manifest, the peer-dependency exemption for published libraries,
  exact override values, the CI range check, and the upgrade workflow (ABIP-7).
- `production-release-branch`: the protected `production` branch, prd deploying only from it, the OIDC trust boundary
  and the promotion flow (ABIP-1).
- `production-key-ceremony`: the live-key inventory, ceremony-only provenance, no developer or client access, and
  repository guardrails against handling keys by hand (ABIP-8).

### Modified Capabilities
- `dependency-security`: the release-age requirement changes from "currently 1440, not lowered" to "at least 10080
  minutes, version-specific exclusions only, enforced in CI", and the lockfile discipline gains ABIP-6's
  dedicated-commit rule (ABIP-6).
- `container-images`: the exceptions requirement changes. `giano-contracts-deployer` leaves the exemption list, so the
  devnet exception is the only one, and every recorded exception must link an issue that exists (ABIP-2).

## Impact

- **Files:**
  - repository root: `AGENTS.md` (new), `CLAUDE.md`;
  - manifests and lockfiles: every `package.json`, both `pnpm-workspace.yaml` files, both lockfiles;
  - `scripts/`: new `check-pinned-versions.mjs` and `check-release-age.mjs`, each with tests;
  - `.github/workflows/ci.yml` (new checks), `.github/workflows/deploy.yml`;
  - infrastructure: `infra/iac/github_oidc.vars.tf`;
  - contracts package: `packages/contracts/Dockerfile.deployer`, the deployer entrypoint, `deploy/cli.ts` (verify-only
    mode);
  - Helm: `deploy/helm/giano` (values and README);
  - docs: `docs/abip-compliance.md`, `docs/key-ceremony.md` (new), `specs/INFRASTRUCTURE.md` §13.1 and §15,
    `packages/contracts/README.md`, `README.md`.
- **Behaviour:** no runtime API or wallet behaviour changes. Contract addresses do not move: ABIP-7 pins only tooling
  and library versions, and the deployer change keeps the release bytecode. The determinism check still guards both.
- **Operations:**
  - DevOps creates the `production` ruleset and runs `terraform apply` for the prd OIDC role;
  - DevOps runs the ceremony that produces the real `CANONICAL_DEPLOYER`, which then unblocks #160's public
    deployment;
  - ABIP-6's 7-day window applies to every third-party package; our own releases are exempt by a recorded
    deviation.
- **Out of scope:**
  - actually running a key ceremony, or rotating any key;
  - stg/prd infrastructure rollout;
  - GitHub Actions SHA pinning, which no ABIP requires.
